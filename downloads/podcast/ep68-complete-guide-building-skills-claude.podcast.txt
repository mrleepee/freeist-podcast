Let's start with the fundamentals. A Skill is fundamentally a folder containing a file called SKILL dot MD written in Markdown with YAML frontmatter, along with optional subfolders for scripts, references, and assets. This simple structure is surprisingly powerful because it provides everything Claude needs to understand not just how to perform a task, but when to apply that knowledge and what tools to use. The folder naming convention uses kebab-case, and the SKILL dot MD file must be named exactly that, case-sensitive, with no variations accepted. This might sound fussy, but it ensures consistency across the entire ecosystem.

The real magic lies in how Skills are designed to load information intelligently. Anthropic calls this progressive disclosure, and it works on three levels. First, the YAML frontmatter is always loaded in Claude's system prompt, helping it decide whether a particular Skill is relevant to the conversation. Second, the main body of SKILL dot MD loads only when Claude determines the Skill applies. Third, linked files in references and assets are discovered only as needed. This three-tier approach minimises token usage while maintaining access to specialised expertise when required. It is elegant design that keeps interactions efficient without sacrificing capability.

There are two other core principles worth understanding. Skills are designed to be composable, meaning Claude can load multiple Skills simultaneously without conflict. Your Skill should work alongside others rather than assuming it has exclusive access to the conversation. Skills are also portable, working identically across em! see! pee! Code, and the API without modification. This portability is crucial because it means the effort you invest in building a Skill today will serve you regardless of how your workflow evolves or which interface you prefer.

The guide uses a rather delicious analogy to explain where Skills fit alongside MCP servers, which you may have encountered. Think of em! see! pee! as providing the professional kitchen with all its tools and ingredients, while Skills provide the recipes with step-by-step instructions. Without Skills, you might connect an MCP server giving you access to powerful tools but have no guidance on what to actually do with them. This leads to confusion, support tickets, and inconsistent results. Skills solve this by embedding pre-built workflows that activate automatically, ensuring best practices are applied every single time.

When it comes to actually building a Skill, the planning phase is absolutely essential. The guide recommends starting with just two or three concrete use cases before writing any code. Each use case should define what triggers the Skill, the multi-step workflow it enables, the tools needed, and the domain knowledge to embed. This sounds like extra work, but it prevents the common mistake of building something too generic that does not really help anyone. The guide identifies three common categories of Skills. The first covers document and asset creation, used for generating consistent high-quality output like presentations, spreadsheets, and frontend designs. The second covers workflow automation for multi-step processes that benefit from consistent methodology. The third covers em! see! pee! enhancement, providing workflow guidance that transforms raw tool access into reliable, optimised workflows.

Now let's talk about the technical requirements, because this is where many people go wrong. The YAML frontmatter is the most important part because it determines when Claude loads the Skill. It requires a name field in kebab-case and a description field under one thousand twenty-four characters that does three things: explains what the Skill does, specifies when to use it, and includes specific trigger phrases users might say. Security restrictions forbid XML angle brackets and prevent reserving names containing "claude" or "Anthropic." Good descriptions are specific and actionable with trigger phrases like "use when user mentions sprint planning, Linear tasks, or project management." Bad descriptions are vague, missing triggers, or overly technical without user-facing language. This is genuinely the difference between a Skill that loads at the right moments and one that either undertriggers or overtriggers constantly.

Writing effective instructions means being specific and actionable, including error handling, referencing bundled resources clearly, and using progressive disclosure by keeping SKILL dot MD focused on core instructions while moving detailed documentation to the references folder. The recommended structure includes numbered steps with expected outputs, examples of common scenarios, and a troubleshooting section. Think of it as writing for a competent colleague who needs clear guidance rather than verbose explanations.

Third, performance comparison to prove the Skill actually improves results versus a baseline without the Skill.

Five key patterns emerged from early adopters worth knowing about. Sequential workflow orchestration handles multi-step processes in a specific order with explicit step ordering, dependencies between steps, validation at each stage, and rollback instructions if something goes wrong. When things go wrong, and they will, the guide offers straightforward troubleshooting. Skills that will not upload typically have incorrect SKILL dot MD naming or invalid YAML frontmatter. Skills that do not trigger need revised descriptions with specific trigger phrases. Skills that trigger too often need negative triggers and more specific scope to prevent irrelevant activation. em! see! pee! connection issues require verifying server status, authentication, and correct tool names. Instructions not being followed are often caused by verbose instructions, buried critical points, or ambiguous language. The guide recommends using scripts for critical validations since code is deterministic while language interpretation is not.
