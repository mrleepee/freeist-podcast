What if I told you that a piece of `eh! eye!` software — something built to help manage inventory — became so complex that it actually started doing its job worse? That's exactly what happened to an agent called Stock Pilot, and the story of how developers fixed it reveals something fascinating about the future of `eh! eye!` development.

Stock Pilot was built incrementally over time, which sounds reasonable until you consider the end result: a four hundred line system prompt, twelve different tools, and multiple subagents all trying to work together. The performance tests showed a troubling drop from around eighty-three percent down to concerning levels. Suddenly, a tool meant to make warehouse operations smoother was actually creating more problems than it solved.

The root causes turned out to be deeply interconnected. The system prompts became overloaded with conflicting policies, essentially giving the agent contradictory instructions. Some tools were doing work that the underlying model could handle perfectly well with basic primitives, while unnecessary information polluted the context window. And perhaps most damagingly, the subagents and orchestrator stopped communicating effectively with each other — imagine a team where everyone speaks a slightly different dialect and nobody's quite sure who's responsible for what.

The solution involved an approach the team called "Hill Climbing" — essentially a methodical, step-by-step process of improvement. They started by running evaluation tests to establish a clear baseline, then carefully analysed where things were going wrong. Crucially, they didn't try to fix everything at once. Instead, they made incremental changes, tested, and repeated. A key part of this was deploying to Claude Managed Agents, which offloads much of the infrastructure headache so developers can focus on the actual design.

The architectural changes were significant. Long system prompts got replaced with packaged, composable information that the system can pull into context as needed — this is called progressive disclosure. Rather than drowning the model in everything at once, you give it what it needs precisely when it needs it. They also shifted toward using human-like primitives — things like code execution, file system navigation, and web search — rather than building custom tools for every possible task. In practice, this meant reducing from twelve tools down to foundational primitives that the platform provides by default.

The evaluation framework they built to measure success had two main categories. Regression tasks test single-turn, realistic scenarios that the agent should handle reliably. Failure mode tasks are more complex, multi-turn situations designed to push the agent into edge cases. They measured both straightforward things like speed and token usage, and used an `el! el! em!` to judge more subjective qualities like tone and style.

What makes this workshop particularly valuable is that it demonstrated a replicable process — using Claude Code to triage failures, identify recurring themes, and systematically modernise an agent's architecture. For anyone building `eh! eye!` systems, the takeaway is that complexity isn't inevitable, and sometimes the smartest thing you can do is deliberately simplify.
