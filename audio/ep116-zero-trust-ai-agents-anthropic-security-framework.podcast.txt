Picture a server that looks exactly like your email tool. Same icon, same shortcuts, same familiar interface. For weeks it sat quietly inside a system, and every time someone sent a message through it, that message got copied somewhere else — silently, without anyone noticing. That was not a thought experiment. That was the first documented attack of its kind, and it happened in the real world, not in a security lab. The people who built it did not need to hack anything. They just needed to trick an AI agent into trusting the wrong tool.

That incident is exactly why, in May twenty twenty-six, Anthropic published a thirty-five page framework called Zero Trust for AI Agents. It is a security blueprint, and it starts from an uncomfortable premise: if you are building with AI agents, you are not just writing software anymore. You are granting a foreign process access to your inbox, your files, your clients' data. The threat model has changed, and most developers are still pretending it has not.

The framework rests on three ideas that sound simple until you try to implement them. Never trust and always verify. Assume breach has already occurred. Grant least privilege. Those are not slogans — they are operational requirements. Static application programming interface keys and shared service accounts are already compromised, according to this document. Not potentially compromised, not maybe compromised. Already compromised. The foundation tier of their maturity model requires short-lived tokens, cryptographically rooted identity, and automated first pass alert triage. That is the baseline.

There is a term from the Open Web Application Security Project called least agency, and it extends the classic least privilege principle. It does not just control what an agent can access — it controls how often, and where. This matters because Microsoft Research has confirmed that large language models cannot reliably tell the difference between information you give them and instructions you meant for them to follow. That is not a quirk. That is a design flaw baked into the architecture, and it means a poisoned memory can corrupt an agent's reasoning long after the original injection happened.

Anthropic's own implementation workflow has eight phases, and their Claude Code product already demonstrates what this looks like in practice. Deny by default permissions, sandboxed execution with operating system-level isolation, session-scoped permissions that expire when the session ends, automatic token refresh for connections, OpenTelemetry metrics for audit trails, and organisation-wide managed settings that enforce policy consistently. They also introduce something called Agentic Security Orchestration, Automation and Response — essentially, a playbook for when an agent does something unexpected.

The United States federal agencies have until twenty twenty-seven to adopt Zero Trust by mandate. But you do not need a government deadline to take this seriously. If you run even one agent that touches a client file, a financial record, a medical intake, you are already in scope. Least agency is not bureaucracy. It is consent applied to software: do not give your agent more power than the task requires, for longer than the session lasts.

Now, here is the uncomfortable part. Anthropic wrote this framework, and of course they want you to take AI security seriously — they also want their tools adopted as the enterprise standard. The principles are sound. The commercial interest behind them is also sound. That does not make the advice wrong. It makes the incentive alignment convenient.

Here is what I want you to do. Right now, before you close this episode, check your Claude Code session permissions. Not next quarter, not after the audit. Now. If your agent has broader access than the task actually needs, that is not a configuration problem. That is a consent problem. Treat that configuration like a password, because somewhere out there, right now, there is a server that looks exactly like the tool you already trust.
