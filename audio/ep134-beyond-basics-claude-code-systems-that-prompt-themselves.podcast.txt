Imagine you could clone yourself and have that clone read every Slack thread, check every dashboard, and understand every internal decision your team has ever made. Now imagine that clone still cannot do your job. That is the situation most developers find themselves in when they first use Claude Code without proper customization.

The fundamental insight from Daisy Holman, an engineer on the Claude Code team, cuts through the AI hype with uncomfortable clarity: if Claude cannot access everything you can access, it cannot truly work alongside you. The agent becomes a sophisticated autocomplete that keeps asking you questions you already know the answers to. Your role as a software engineer is shifting from writing code yourself to creating what Holman calls clones of yourself that scale across many agents. This is not science fiction; it is the current state of agentic development tooling, and understanding it separates productive workflows from expensive disappointments.

The customization needed to make this work falls into three distinct categories. The first is access. Claude needs connectivity to your information sources or it operates blind. Team chat logs explain why decisions were made, not just what was decided. Continuous integration systems are places where agents genuinely excel because they thrive on fixing concrete failures. Dashboards and production monitoring give them eyes on systems you care about. Internal documents, design documents, operational runbooks, and meeting notes contain the institutional memory that cannot be trained into any model no matter how much compute you throw at it.

Holman offers a practical exercise: try working an entire day without leaving Claude Code. Note every tool you switch to. Then connect Claude to those tools. You will discover exactly how much context you take for granted and how much the agent is missing.

The second category is knowledge. Here is where many teams waste enormous amounts of money on fine-tuning. Frontier models evolve so rapidly that anything you train today becomes obsolete tomorrow. The cost-benefit simply does not work. Instead, use in-context learning. All customization is fundamentally just text files that the model reads when it needs them. Conventions, recent changes, internal application programming interfaces, and team-specific vocabulary live in these files. The agent learns by reading, not by training.

The third category is tooling. Holman draws a sharp analogy: out of the box, Claude Code has basic edit tools that are like comparing the ancient text editor ED to a modern integrated development environment. Syntax highlighting, language server protocols, intelligent code completion, and those red squiggly underlines that flag errors before you run anything. None of that exists by default for agents. The equivalent for agents is post-tool-use hooks that provide non-blocking reminders. A linter that says hey, you just modified that authentication function, did you remember to check the permission boundaries. The fastest way to make your agent better is a tighter feedback loop, not a smarter model. This is the most underappreciated insight in the entire field.

The context window constraint makes all of this harder. Frontier models have plateaued around one million tokens as their maximum input. Every customization you add must fit inside that fixed window. Holman's analogy is brutal and accurate: it is like running the Node Package Manager on an Arduino. Extremely limited space forces intentionality. The principle is zero-overhead abstraction: do not pay for what you do not use.

There is a technical complication with KVCache that most people ignore. If you change anything early in the system prompt, the entire cache invalidates and every subsequent token becomes ten times more expensive to process. The guideline is counterintuitive: put stable, shared information at the front of your context and keep volatile, per-task information near the end. The things that change constantly should be last because they invalidate less cached work.

Four primitives structure the agentic harness. The Model Context Protocol was designed for simple chatbots without shell access. It does not scale well because every tool's name, description, and schema goes into the system prompt and consumes precious context space. The rule of thumb is use skills for internal developer tooling and use the Model Context Protocol for shipping integrations to non-technical customers.

Skills are simpler: a folder with a markdown file and a one-line description in the front matter. Easy to create but prone to quality control issues at scale. The description is always loaded which costs some tokens, and reliably triggering a skill can require three to four hundred tokens of context. There is currently no hierarchy system for lazy-loading subskills, though the team is working on it.

The key recommendations crystallize from all of this. Connect Claude to all your information sources. Prefer tools that scale with intelligence over tools that hard-block behavior. Use skills for internal developer tooling, the Model Context Protocol for external integrations. Be intentional with your context window like it is a constrained resource you cannot expand. Implement hooks and linters as red squiggly reminders, not hard blockers that stop the agent dead.

The team is exploring hierarchy systems for skills, using Claude Code internally to develop Claude Code, and continuing to optimize context engineering. The future belongs to developers who understand that the bottleneck is not the model's intelligence but their ability to give it the right context in the right way.
