In two thousand seven, a Finnish engineer lost access to a proprietary version control tool on a Tuesday and spent the following weekend building a replacement. Two weeks later, he had created Git. The Linux kernel it would eventually manage contains over twenty-two thousand files and thousands of contributors. No corporation funded this. No government mandated it. No committee approved it.

That engineer was Linus Torvalds, and he wrote the first version of the Linux kernel back in nineteen ninety-one. For the next decade and a half, he managed the project's code using tarballs and patches — essentially compressed archives and handwritten instructions for what to change. It worked, but barely. When the proprietary tool called BitKeeper became unavailable in two thousand seven, Torvalds had a problem that demanded an actual solution.

What he built in those two weeks was not a polished product. It was a tool born from deep frustration with everything that came before it. Torvalds had publicly expressed contempt for the Concurrent Versions System and for Subversion, the two dominant version control systems of the era. His complaint was not merely technical. He despised how those systems lied about the state of code — how they obscured what had actually changed, masked conflicts, and presented a clean fiction over messy reality. Git was designed to tell the truth about what was happening to a codebase, even when that truth was ugly.

This honesty turned out to be exactly what the open-source world needed. Git tracks content rather than individual files, which means it records the actual state of everything in a project at every moment. Each version of the entire codebase gets a unique identifier called a Secure Hash Algorithm One hash. Change a single character in one file, and the hash for the whole project changes. This is not cryptography protecting secrets. It is a tamper detector built into the fabric of the system. If something gets corrupted or tampered with, Git knows. More importantly, everyone using the repository knows.

The practical consequences of this design are striking. A new branch in Git requires roughly forty-one bytes of disk space. On a laptop five years old, Git can diff the entire Linux kernel in under one second. The Linux kernel project averages four and a half merges per day, meaning four and a half times every twenty-four hours, someone integrates new code from a contributor into the main codebase. That pace would be impossible without a system that developers actually trust.

Trust, for Torvalds, is not abstract. His model for the Linux kernel involves a network of specific human beings — between five and fifteen people he personally knows and relies upon to validate contributions. This is not bureaucracy. It is a deliberate structure built on professional relationships rather than institutional authority. The kernel grew to twenty-two thousand files and thousands of contributors precisely because Git made that scale manageable without a central authority deciding who could contribute and who could not.

Critics will note that Git's dominance today owes something to GitHub and corporate investment, that companies adopting it played as much a role as the original design. That is fair. But the causality runs in a specific direction. Corporations did not invent Git and then persuade developers to use it. Developers adopted Git first because it solved a real problem honestly, and corporations followed because they had no better option. Git succeeded because it was designed according to principles that made sense to the people using it, not to the markets trying to monetise it.

Here is what that means for anyone building or managing software today. The infrastructure you rely on every single day — the systems that handle your code, your deployments, your collaborative work — was largely built by people solving their own problems. That includes Git, but it also includes the network of tools and standards that surround it. None of it was designed by a committee with your interests in mind. It was designed by someone who needed it to work, and who refused to accept a system that pretended to work while actually lying.

The next time someone tells you that reliable infrastructure requires institutional backing, corporate governance, or some form of central authority to ensure quality and trust, consider this. The entire Linux kernel — every server, every Android device, every piece of critical software running somewhere right now — runs on two weeks of weekend coding and a stubborn refusal to accept a lie as the truth. What are you waiting for?
