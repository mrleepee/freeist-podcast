Here's a thought that might keep you up tonight: the most productive software engineers of the next five years won't be the ones who learn to write better code. They'll be the ones who figure out how to clone themselves across dozens of AI agents.

This episode covers "Beyond the Basics with Claude Code," a talk by Daisy Holman from the Claude Code team at Anthropic. Her central argument is quietly revolutionary. If an AI can't access everything you can, it simply cannot do your job with you. Full stop. The engineer who learns to give their AI assistant the same information access, institutional knowledge, and tooling as themselves will multiply their output in ways that make headcount irrelevant. Daisy breaks this down into three categories of customization, each with counterintuitive implications.

The first is access. Agents need connectivity to your information sources: the team chat where decisions get explained in Slack threads, the continuous integration and delivery pipelines where agents genuinely excel at debugging failures, the production monitoring dashboards, and the internal documents including design documents, runbooks, and meeting notes. Daisy's tip is wonderfully practical. Try working an entire day without leaving Claude Code. Note every tool you switch to. Then connect Claude Code to those tools. The gap between what you can access and what your agent can access is where half your productivity is hiding.

The second is knowledge. Here's where fine-tuning enthusiasts often go wrong. Institutional memory cannot be trained into the model because frontier models evolve too quickly for fine-tuning to be cost-effective. Instead, use in-context learning. All customization lives in text files, and when something changes, you update a file rather than retraining a model. This approach adapts far faster than fine-tuning ever could.

The third category is tooling. Out of the box, Claude Code has basic edit tools, which Daisy compares to working in an ancient line editor rather than a modern integrated development environment. Think of what you're building as an agentic integrated development environment. The equivalent of those helpful red squiggly underlines that catch errors without blocking you is a set of post-tool-use hooks that provide non-blocking reminders. One of Daisy's sharpest observations is this: the fastest way to make your agent better is a tighter feedback loop, not a smarter model. And crucially, prefer tools that scale with intelligence over tools that compensate for lack of intelligence. Hard blockers that prevent the agent from doing something stupid often prevent it from doing something brilliant too.

Now let's talk about context window constraints, because this is where most people stumble. Context windows have plateaued at approximately one million tokens for frontier models, and every customization must fit inside this fixed window. Daisy uses a perfect analogy: it's like running a package manager on extremely constrained hardware. The zero-overhead abstraction principle applies directly here. Do not pay for what you do not use. There's a subtle but critical complication with the key value cache. Changing anything early in the prompt invalidates the entire cache, making all subsequent tokens dramatically more expensive. The guideline is to put stable, shared information at the front and keep volatile, per-task information near the end.

For scaling, Daisy describes four key primitives: the Model Context Protocol, skills, hooks, and agents. The Model Context Protocol is designed for simple chatbots without shell access, and it does not scale. Each tool's name, description, and schema goes into the system prompt, and that prompt has a finite size. The solution is tool search, which lazy-loads tool definitions. Only the most generic tools, like edit and bash, stay in the system prompt. Skills, by contrast, are a folder with a markdown file and a one-line description in the front matter. They're easy to create and developer-friendly, but they can lead to quality control issues at scale. The description always loads, and reliably triggering a skill can take three to four hundred tokens. The team is actively building hierarchy systems for skills to address this.

What does all this mean in practice? Five concrete recommendations. Connect Claude Code to all your information sources, because this single change is likely the highest impact thing you can do. Prefer tools that scale with intelligence over tools that hard-block behaviour. Use skills for internal developer tooling and the Model Context Protocol for external integrations. Be intentional with your context window and treat it as a genuinely scarce resource. And implement hooks and linters as reminders, not blockers. The goal is to treat AI not as a chatbot you query, but as a version of yourself that scales.
