Most teams building AI analytics tools assume the hard problem is getting the language model to write good SQL. Here's the thing though — at Anthropic, when they gave their analytics agent direct grep access to thousands of prior SQL queries, accuracy barely moved. The information was there, the agent saw it, and it still did not use it. The bottleneck was never the code generation. The bottleneck was helping the model retrieve the right information in the first place.

That finding reshaped how Anthropic approached self-service analytics entirely. They stopped optimising for better SQL generation and started solving the context and verification problem. The result? Roughly ninety-five percent of their business analytics queries now run automatically with about ninety-five percent accuracy in aggregate, freeing the data science team to focus on causal modelling, forecasting, and machine learning.

The core issue Anthropic identified comes down to three failure modes that account for the vast majority of inaccurate responses. First, there's concept-entity ambiguity — with hundreds of viable options in a data model out of potentially millions of fields, the agent simply cannot choose the correct ones without guidance. Measuring something like active users sounds simple until you ask what actions constitute activity, whether to include fraudulent accounts, and what lookback window to use. Second, data staleness — business definitions, schemas, and data sources change constantly, and assets go stale, returning subtly wrong answers that look perfectly reasonable. Third, retrieval failure — the right information exists in the data model and is properly annotated, but given the vastness of the search space, the agent does not find it.

To address these failure modes, Anthropic built what they call an agentic analytics stack. The foundation is the most important layer: if revenue resolves to one governed dataset instead of forty plausible candidates, the ambiguity problem largely disappears before the agent ever has to search. They call these canonical datasets — fewer, more heavily governed logical models that are clearly owned, consumption-ready, and discoverable. Near-duplicates are aggressively deprecated. Governance gets enforced by tooling that structurally routes the agent to canonical models first, by continuous integration that makes changes bypassing them fail review, and by mandate. Nearly all data code lives in a single repository with CI checks that protect cross-layer integrity — if a modelling change would break a downstream dashboard or invalidate a documented metric, the CI flags it. Metadata is treated as a first-class product: column and table descriptions, canonical metric definitions, grain documentation, valid value ranges, lineage, ownership, and model tiering maintained with the same rigour as transformations themselves.

The sources of truth the agent consults sit in a hierarchy of trust. At the top sits the semantic layer — compiled metric and dimension definitions. If a question maps cleanly to a defined metric, the agent calls a function and gets one number, the same number every other surface produces. Agents are structurally required to leverage the semantic layer first. One thing they tried and found net-negative was auto-generating metric definitions with LLMs — it encoded the very ambiguities they were trying to eliminate. Their recommendation: use AI to generate documentation, but have humans own the definitions. Below the semantic layer sit lineage and transformation graphs that let the agent reason about which upstream models feed a concept, which are deprecated, and which share grain. Below that, a query corpus of historical SQL from dashboards, notebooks, and prior analyses. Here is the thing about the corpus — giving the agent raw retrieval access to thousands of prior queries moved accuracy by less than a single point. The information was there, the agent saw it, and it still did not use it. What works is distilling that corpus into structured per-domain reference documents and reusable analysis patterns. The layer most teams skip entirely is business context. An agent that does not understand the business will answer what the user asked but not what they meant. Anthropic pipes in a company knowledge graph of indexed documents, roadmaps, decision logs, and organisational structure.

The single biggest lever they found was something called skills. Without skills, Claude's ability to answer analytics questions accurately did not exceed twenty-one percent on their evaluations. Adding skills gets numbers consistently above ninety-five percent in aggregate and regularly around ninety-nine percent in certain domains. In Claude Code, a skill is a folder of markdown the agent reads on demand. Key patterns include pairwise skills — a knowledge skill acts as a thin top-level router telling the agent to try the semantic layer first, then load domain-specific reference files. An analyst skill encodes the process a senior analyst would follow: clarify the question, find sources, run the query, and loop through adversarial review sub-agents. Reference documents are written specifically for retrieval by a large language model, describing tables, grain, scope, exclusions, gotchas, and explicit routing triggers without prescriptive recipes that go stale.

Skill maintenance turned out to be a first-class engineering problem. Skill documents describe a data model that changes daily. Without active maintenance, they are wrong within weeks. Anthropic watched their offline accuracy drift from approximately ninety-five percent at launch to roughly sixty-five percent over a single month before they treated this as an engineering problem. The solution was to colocate skill markdown in the same repository as transformation models, with a code-review hook flagging any reporting-model change that does not touch a skill file. Roughly ninety percent of data-model pull requests now include a corresponding skill change.

For validation, Anthropic runs offline evaluations with question and answer pairs auto-generated by AI then human-validated. Every correction from a stakeholder becomes a candidate evaluation. They gate launches per domain — a domain owner cannot announce an agent until their evaluation slice clears around ninety percent. Online, they use adversarial review — a Claude skill that aggressively challenges all underlying assumptions on a potential final answer. This increased accuracy by six percent but at thirty-two percent more tokens and seventy-two percent higher latency, so it is deployed selectively. Every response carries a provenance footer showing source tier, data freshness, and model owner — this does not make the answer more correct, but helps the consumer judge trustworthiness. They also have passive monitoring tracking the share of queries resolving through the semantic layer and the share of responses with correction language, plus active correction harvesting where a scheduled agent scans stakeholder channels for corrections, drafts fixes to reference documents, and opens pull requests tagged to domain owners. The silent failure mode none of this fully catches is the answer that is wrong but looks plausible and gets used without objection.

The takeaway is this: most analytics teams are solving the wrong problem. They pour resources into better SQL generation when the real challenge is helping the model retrieve the right information and verify it is correct. Anthropic's experience suggests that solving this does not require enormous infrastructure or cutting-edge models. A handful of canonical datasets, a few dozen offline evaluations, and a thin knowledge skill will capture most of the upside. The bottleneck was never access to information. The bottleneck was whether your data model makes it obvious which information matters. Once that is solved, the SQL almost writes itself.
