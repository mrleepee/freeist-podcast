Imagine you spend months training an AI to write code, then watch it produce a thirty page architecture plan that you cannot actually read. That is not a hypothetical. That is what is happening right now inside software teams everywhere, and a blog post published by Anthropic in May twenty twenty-six went viral precisely because it named the problem nobody wanted to admit.

The engineering lead for Claude Code, a man named Thariq Shihipar, posted something that racked up four point four million views in sixteen hours. The title was deliberately provocative: "The Unreasonable Effectiveness of HTML." His argument was not academic. It was uncomfortable. The format that the entire industry settled on for AI outputs, the trusty Markdown file that everyone has been generating since the G P T four era, is actively holding AI agents back. HTML is the upgrade nobody asked for but everybody needs.

Here is the practical problem. When Claude Code takes on larger tasks, the outputs grow proportionally. A thirty line checklist in Markdown is perfectly readable. A three hundred line implementation plan, research report, or code review rendered as a wall of text is not readable just because it technically renders. The information is technically there, but the format provides no handles. You scroll past it, you skim it, you approve it, and you move on. That is not review. That is rubber-stamping with extra steps.

HTML gives the model a richer surface to organise information. Tables for dense comparisons. Cascading style sheets for visual hierarchy. Scalable vector graphics for diagrams that do not break on every screen width. JavaScript for local interactions, tabs for navigation, copy buttons for exporting output back into your workflow. Shihipar backed the argument up with twenty working examples, each one a self-contained HTML file that an agent produced instead of the usual Markdown wall. Code reviews with colour-coded severity labels and inline annotations. Stakeholder reports with collapsible sections. Design systems with live colour swatches you can inspect. Architecture diagrams you can actually interact with instead of ASCII art that looks decent in a wide terminal window and broken everywhere else.

Simon Willison, who has spent considerable time building things with large language models, picked up on the post immediately and started experimenting. His observation cuts to the heart of why the Markdown convention stuck in the first place. During the G P T four era, context windows were tiny by current standards, around eight thousand tokens. Markdown's relative token efficiency over HTML was genuinely worthwhile. You traded richer formatting for being able to fit more content in the box. But context windows have exploded since then, and that tradeoff no longer holds. Asking Claude to produce an explanation in HTML means it can drop in vector diagrams, interactive widgets, and in-page navigation links, things that make information genuinely navigable rather than merely present.

The practical pattern that emerges is straightforward. Instead of asking the model to write a plan for refactoring the billing module, you ask it to create an HTML artifact that explains the billing refactor. Include a module map. List the key file changes. Flag risks by severity. Lay out a staged migration plan. Provide a copyable implementation prompt. The underlying request is identical. The second format is easier to inspect, easier to share, and easier to drop back into a later Claude Code session as durable project context. HTML becomes a working document. The Markdown plan was a one-time response.

This connects directly to something Anthropic shipped alongside this thinking, a feature called dynamic workflows that arrived with the Opus four point eight release. Dynamic workflows are JavaScript scripts that orchestrate subagents at scale. The model writes the script for your task, and a runtime executes it in the background while your session stays responsive. The key shift is architectural. Instead of Claude deciding turn by turn what to spawn next, with every intermediate result landing in its context window, a workflow script holds the loop, the branching logic, and the intermediate results itself. The model holds only the final answer.

Now think about what happens when you combine rich HTML output with workflow orchestration. A single workflow can spawn dozens of agents, up to one thousand per run, each producing findings. The results get synthesised into an HTML artifact that gives the human reviewer actual handles. Scan the overview. Inspect the diagram. Compare options side by side in a table. Jump directly to risks. Tweak a slider. Copy the selected output back into Claude Code. This is not cosmetic. This is about control. As agents handle bigger chunks of work, the risk is that humans stop reading what agents produce. Long Markdown plans are easy to approve without deeply reviewing. HTML can reduce that failure mode.

Shihipar is not arguing that Markdown should be abandoned entirely. Markdown remains the right tool when the output is small, when it needs to play nicely with version control diffs, when humans will edit it manually, or when tooling elsewhere in your pipeline expects Markdown. The practical rule is clean: use Markdown when the output is mostly text and will be edited by humans. Use HTML when the output needs layout, diagrams, dense comparison, interactivity, or a better reading experience.

The pushback arrived predictably. Team HTML declared Markdown dead. Team Markdown fired back with security concerns about AI-generated JavaScript, noisy diffs that break code review workflows, and token overhead that inflates your A P I bill. Both sides have legitimate points. HTML artifacts should be treated as disposable. Their value is in helping a human make a better decision right now, not in becoming permanent documentation that quietly rots over eighteen months.

The deeper point here is about the interface between humans and AI agents. The bottleneck in AI-assisted development is no longer code generation speed. It is the interface through which humans stay cognitively connected to what agents produce. Markdown was adequate when AI output was short and simple. It is not adequate when agents are generating architecture plans, code reviews, research reports, migration strategies, and incident analyses. The format shapes the review, and the review shapes the outcome. Anthropic's own Claude Code team is using their own tools and publishing the evidence that HTML outputs produce better human decisions. That is more convincing than any theoretical argument about markup languages.

The real takeaway is not about HTML versus Markdown. It is about treating the output format as part of the workflow design. Teams that ask agents to produce artifacts designed for review, with navigation, visual hierarchy, and export mechanisms, will stay more in control than teams that keep approving walls of text. The format is the interface, and the interface is the lever.
