Imagine handing a brilliant colleague a computer with no internet access, no email, and no idea what your team has been working on for the past six months. That is exactly what most software engineers are doing when they use AI coding assistants out of the box, and. Daisy Holman, an engineer on the Claude Code team, has been thinking about this problem seriously, and her conclusion is uncomfortable: if your AI cannot access everything you can, it cannot do your job with you.

The core insight driving her work is elegant in its simplicity. Your role as a software engineer is fundamentally changing. You are no longer just writing code yourself. You are creating clones of yourself that can scale across many agents simultaneously. That means the real skill is not writing code faster. It is building the systems that make those clones effective.

There are three categories of customisation that matter. First, access. Agents need connectivity to your information sources. Team chat explains why decisions were made, not just what was decided. Continuous integration and deployment systems are places where agents genuinely excel, particularly at fixing failures. Dashboards, production monitoring, internal documents, design documents, runbooks, meeting notes. Holman suggests trying an entire day without leaving your AI coding tool. Note every tool you switch to. Then connect your AI to those tools. That exercise alone will transform what you can accomplish.

Second, knowledge. Institutional memory cannot be trained into the model. Conventions, recent changes, internal application programming interfaces, vocabulary specific to your codebase. Fine-tuning looks attractive but it is not cost-effective. Frontier models evolve too quickly. The better approach is in-context learning, which means all your customisation lives in text files that the model reads when it needs them.

Third, tooling. Think of the agentic integrated development environment. Out of the box, your AI has only basic edit tools, like comparing modern code editors to something from the nineteen seventies. Missing are syntax highlighting, language server protocols, code completion, and those red squiggly underlines that catch mistakes before they become bugs. The red squiggly equivalent for agents is post-tool-use hooks that provide non-blocking reminders. Here is the counterintuitive part Holman emphasises: the fastest way to make your agent better is a tighter feedback loop, not a smarter model.

She makes a useful distinction between two types of tools. Some tools compensate for lack of intelligence, hard-blocking behaviour that the model cannot handle safely. Avoid those. Prefer tools that scale with intelligence. When the model gets better, these tools become more powerful automatically.

Now, context windows have plateaued at around one million tokens for frontier models. That sounds enormous until you realise every customisation you add must fit inside this fixed window. Holman uses an analogy that stuck with me: running Node Package Manager on an Arduino. Extremely limited space means you must be deliberate about what you include. Apply the zero-overhead abstraction principle. Do not pay for what you do not use.

There is a complication with key-value cache. If you change anything early in your prompt, you invalidate the entire cache, making all subsequent tokens ten times more expensive to process. The practical guideline is to put stable, shared information at the front of your configuration. Keep volatile, per-task information near the end. This simple habit will dramatically improve performance.

On plugin abstractions, Holman breaks down four key primitives: the Model Context Protocol, skills, hooks, and agents. The Model Context Protocol was designed for simple chatbots without shell access. Use skills for internal developer tooling. Use the Model Context Protocol for shipping integrations to non-technical customers. Here is the catch with that protocol: it does not scale. Each tool's name, description, and schema goes into your system prompt, and that eats into your context window fast. The solution is lazy-loading through tool search, where only generic tools like edit and bash stay permanently loaded.

Skills are simpler. A folder with a markdown file inside and a one-line description in the front matter. Easy to create, which is both a strength and a weakness. Quality control becomes an issue at scale. The description is always loaded, which costs some tokens, but reliably triggering a skill can still take three to four hundred tokens. Currently there is no hierarchy system for lazy-loading subskills, though that is on the roadmap.

What does all this mean in practice? Connect your AI to all your information sources. Prefer tools that scale with intelligence over tools that hard-block behaviour. Use skills for internal developer tooling, the Model Context Protocol for external integrations. Treat your context window like a constrained resource, because it is. Implement hooks and linters as helpful reminders, not authoritarian gatekeepers.

The team is exploring hierarchy systems for skills, using Claude Code to develop Claude Code, and continued optimisation of context engineering. The frontier is moving fast. Build your clones well.
