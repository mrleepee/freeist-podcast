What if I told you that a large language model could read through thousands of correct answers, sit right next to the information it needed, and still give you the wrong one? That is not a hypothetical. Researchers at Anthropic ran exactly this experiment, and the results should change how every organisation thinks about deploying AI for data analytics.

The core finding from their internal rollout is deceptively simple: analytics accuracy is a context and verification problem, not a code generation issue. The hard part is not writing SQL. The hard part is mapping what a business user actually means by "revenue" or "active user" to the correct column in the correct table. Solve that mapping problem, and the code practically writes itself. Get it wrong, and no amount of clever prompting will save you.

At Anthropic, they automated ninety-five percent of routine business analytics queries using Claude, and the system maintains roughly ninety-five percent accuracy across the board. That is a remarkable number. But what makes it remarkable is not the AI magic. It is the unglamorous engineering underneath: canonical datasets, a semantic layer, carefully maintained reference documentation, and a skills framework that took accuracy from a woeful twenty-one percent to above ninety-five. Let me walk through how they got there.

The first thing Anthropic discovered is that data is not software. Coding agents thrive in open-ended problems where creativity is rewarded and tests provide natural checkpoints. Analytics is the opposite. Usually there is exactly one correct answer from exactly one correct source, and no deterministic way to prove you have found it. On top of that, the end user is often not a data expert. They are a sales manager or a product lead acting on behalf of someone who cannot validate whether the numbers are right. That fundamentally changes where the engineering effort belongs. Not in fancier SQL generation, but in better context and better structure.

They identified three failure modes that account for the vast majority of inaccurate responses. The first is concept-entity ambiguity. A data model might contain hundreds of viable options for something like "active user." Which actions count as activity? Do you include test accounts? What lookback window are you using? Without clear resolution, the agent is guessing. The second is data staleness. Business definitions, schemas, and data sources change constantly, and assets that were accurate last month quietly start returning subtly wrong answers. The third is retrieval failure. The right information exists, is properly annotated, and is sitting exactly where it should be, but the agent simply does not find it in the vastness of the search space.

The solution is an agentic analytics stack built in layers, each one tackling one or more of those failure modes.

The foundation is the most important layer: the data itself. If the word "revenue" resolves to one governed dataset instead of forty plausible candidates, the ambiguity problem largely disappears before the agent ever has to search. Anthropic curated a small set of canonical, single source-of-truth datasets that are clearly owned, ready to use, and easy to discover. They aggressively deprecated near-duplicates and enforced these standards through tooling and continuous integration. Nearly all their data code lives in a single repository with automated checks that flag any modeling change which would break a downstream dashboard or invalidate a documented metric. Metadata is treated as a first-class product. Column descriptions, grain documentation, valid value ranges, ownership, and model tiering are maintained with the same rigour as the transformations themselves.

Above that sits the sources of truth layer, which the agent consults in a strict hierarchy. First is the semantic layer: compiled metric and dimension definitions that let the agent call a function and get one number, the same number every other surface produces. Agents are structurally required to use the semantic layer first. Interestingly, they tried auto-generating metric definitions with large language models and it was net-negative. It encoded the very ambiguities they were trying to eliminate. The recommendation is to use the model to generate documentation but have humans own the definitions.

When the semantic layer does not cover a question, the agent turns to the lineage and transformation graph, which lets it reason about which upstream models feed a concept, which are deprecated, and which share grain. Below that is the query corpus: historical SQL from dashboards, notebooks, and prior analyses. Here is where that striking experiment comes in. Anthropic gave the agent direct retrieval access to thousands of prior SQL files. The answers were in there about eighty percent of the time. The agent read them. Accuracy did not improve. The information was there, the agent saw it, and it still did not use it. What works is not raw access but distilling that corpus into structured per-domain reference documents and reusable analysis patterns.

The final source of truth is business context, which most teams skip entirely. An agent that does not understand the business will answer what the user asked but not what they meant. Anthropic pipes in a company knowledge graph of indexed documents, roadmaps, decision logs, and organisational structure.

Then comes the skills layer, and this is where the numbers get interesting. Without skills, Claude's ability to answer analytics questions accurately did not exceed twenty-one percent on their evaluations. Adding skills gets that number consistently above ninety-five percent and regularly around ninety-nine percent in certain domains. A skill is essentially a folder of markdown that the agent reads on demand. Key patterns include pairwise skills where a thin knowledge skill acts as a top-level router, directing the agent to try the semantic layer first and then loading domain-specific reference files, while an analyst skill encodes the process a senior analyst would follow: clarify the question, find sources, run the query, loop through adversarial review sub-agents.

But skills require maintenance. Skill documentation describes a data model that changes daily. Without active maintenance, the docs were wrong within weeks. Anthropic watched offline accuracy drift from about ninety-five percent at launch to about sixty-five percent over a month before they treated this as a first-class engineering problem. The solution was to colocate skill markdown in the same repository as the transformation models. A code review hook now flags any reporting model change that does not touch a skill file. Roughly ninety percent of data model pull requests now include a skill change.

The final layer is validation, and this is where the adversarial review sub-agents earn their keep. One sub-agent skill aggressively challenges all underlying assumptions on a potential final answer. It improved accuracy by six percent but costs thirty-two percent more tokens and adds seventy-two percent higher latency. Every response also carries a provenance footer indicating source tier, data freshness, and model owner. That does not make the answer more correct, but it helps the consumer judge how much trust to place in it.

What none of this fully catches is the silent failure: an answer that is wrong but looks plausible and gets used without objection. The mitigations are provenance footers, explicit human sign-off on leadership-bound answers, and standing evaluations for key performance indicators.

If you are starting from zero, Anthropic's advice is blunt: a handful of canonical datasets, a few dozen offline evaluations, and a thin knowledge skill will capture most of the upside. Everything else they describe is what they added once those basics were working.

The broader lesson is that the bottleneck in analytics AI is not access to information. It is the structure that lets an agent know which information to trust. Build that structure, and the accuracy follows.
