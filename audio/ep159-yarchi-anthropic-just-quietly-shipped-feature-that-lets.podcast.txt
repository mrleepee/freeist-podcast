Most software projects fail because the coordination is bad, not the code. A developer writes something, hands it to a tester, the tester breaks it, sends it back, and that loop eats time nobody has. Anthropic quietly shipped a feature inside Claude Code that lets you simulate an entire engineering team in your terminal. They call it Agent Teams. One main Claude Code session acts as the orchestrator and spawns two to five specialized agents that work in parallel. A front-end agent, a back-end agent, a quality assurance agent. The difference between this and standard sub-agents is that these agents talk to each other directly. A developer agent hands its code to a QA agent without you playing middleman.

The setup is experimental. You enable it by adding a specific environment variable to a local settings file in your project directory. But here is the move that matters. Before you write a single prompt, pull the official Claude Code Agent Teams documentation and save it as a local markdown file. Feed that file into your orchestrator session. Now the AI has the master reference for how to operate its own team. Without that, you are asking a foreman to build a house without blueprints.

The prompting strategy is where most people will fail. These sub-agents wake up with zero conversational context. They do not know your project history. They do not know your architecture decisions. You must establish the goal, define each role, state exactly what each agent should produce, and map the communication flow. Tell the front-end agent exactly who it messages when it finishes a component. Tell the QA agent exactly when to pass work back to the orchestrator.

If you are building your own agentic systems, apply the file ownership rule from this feature. Assign each agent specific files it is allowed to edit. Without strict file ownership, parallel agents overwrite each other silently and you lose work.

The cost is real. Running three agents burns three times the tokens. If your task is simple or sequential, standard sub-agents are the better tool. Agent Teams exist for parallel work with clear boundaries between responsibilities. Use the tmux tool for a split-pane view so you can watch each agent think and intervene when one goes idle. An idle agent means your prompt lacked a clear dependency.

Always have agents save progress to temporary files. Always send a clean shut-down request from the orchestrator before closing. Otherwise you lose everything in flight. The tool is powerful. It is also expensive and unforgiving. Treat it like a team of contractors. Give them clear scopes, watch the work, and never assume they will coordinate without explicit instruction.
